# 新增音频格式支持：接入与排障指南

> 最后更新：2026-08-01
> 来源：APE MVP 的实现与实机排障。本文记录可复用的方法；APE 的具体结论作为案例保留。

---

## 1. 为什么“能够解码”不等于“已经支持”

Mica 的格式支持是一条端到端链路：

```text
扫描/识别
  → MIME 与元数据
  → Extractor 解复用、帧边界与时间戳
  → Renderer/Decoder 选择
  → FFmpeg JNI 与 PCM 输出缓冲区
  → AudioProcessor（频谱、EQ、格式转换等）
  → AudioTrack
  → seek、切歌、失败恢复和 UI 状态
```

任何一层的假设不成立，都可能表现成“不能播”“自动跳歌”“拖动失败”“开头异响”或“声音正常但频谱卡顿”。新增格式时不能只验证 FFmpeg 是否认识 codec。

如果链路包含 JNI 或其他 native 代码，必须对项目声明的每个 ABI 分别构建并检查产物；当前发布配置包含 `arm64-v8a` 和 `armeabi-v7a`。只验证 64 位 so、只扩大 `abiFilters` 或只在模拟器上编译，都不能证明 ARMv7 包可安装并能播放。

## 2. 推荐的接入顺序

### 2.1 先建立格式事实

准备至少三类样本：

- 普通文件：常见采样率、位深和声道数。
- 边界文件：超大压缩帧、长静音开头、短文件、最后一帧不满。
- seek 文件：时长较长、有明显时间标记，便于判断定位是否准确。

用标准 FFmpeg/ffprobe 保存基准事实：

- codec、容器版本、采样率、声道数、位深和总时长；
- 前几包的 offset、size、PTS、duration 和哈希；
- 解码后 PCM 的长度、首个非静音采样位置、峰值和哈希。

这些数据用于区分“源文件本来如此”和“应用产生了错误”。不要仅凭听感反推数据层问题。

### 2.2 接入扫描、MIME 与能力路由

检查以下入口是否一致：

- 扩展名能否进入曲库扫描；
- MIME 是否在元数据探测、播放路由和诊断中保持一致；
- `MicaExtractorsFactory` 是否注册对应 Extractor；
- `FfmpegLibrary` 能否把 MIME 映射到正确的 FFmpeg decoder；
- Renderer 支持策略是否会误选平台 decoder，或提前将格式判为不支持。

这一层错误通常表现为文件不入库、立即报不支持、准备阶段失败，或者还没读取媒体数据就跳歌。

### 2.3 实现并单独验证 Extractor

容器解析至少要正确处理：

- 文件头、版本和可选区段；
- 压缩帧起点、长度和对齐；
- 每帧对应的采样数；
- 最后一帧的特殊长度；
- PTS、duration 和总时长；
- seek table，以及目标时间到帧号/文件偏移的映射。

验证 Extractor 时，优先比较应用输出的压缩 packet 与标准 demuxer：

1. packet 数量；
2. 前几包及 seek 后首包的 offset、size；
3. packet 内容哈希；
4. PTS 与 duration。

如果这些完全一致，就应停止反复修改 Extractor，继续向 decoder/JNI/PCM 链路缩小范围。

### 2.4 验证解码器的 PCM 契约

不能只检查 decoder 返回成功，还要核对：

- 输出 encoding、采样率、声道数；
- 单次输出可能达到的最大字节数；
- 输出 ByteBuffer 的 position、limit 和实际写入长度；
- flush/reset/seek 后是否会复用旧数据；
- 多次扩容后，已写数据和当前写指针是否都被保留；
- 应用 PCM 与标准 FFmpeg PCM 是否一致。

推荐使用只读、限量的诊断探针：只记录前一到两个输出 buffer 的长度、首个非静音位置、局部峰值和 SHA-256。探针不得移动生产 ByteBuffer 的 position，也不得改变音频内容；定位完成后必须移除。

### 2.5 验证下游处理器的“数据时钟”假设

压缩帧大小与最终播放粒度不是一回事。某些格式可能一次解出一秒以上 PCM，而 AudioTrack 仍按自己的节奏播放。

频谱等旁路消费者应遵循实际播放状态和播放时钟，不能把“decoder 刚输出的数据”当成“用户此刻听到的数据”。同时检查：

- 队列容量是否覆盖格式可能产生的最大合理 burst；
- 容量策略是否有明确上界；
- burst 到达时是否丢弃或覆盖尚未消费的数据；
- pause、seek、切歌和 flush 后是否清理旧时间线；
- 消费推进是否跟随真实播放状态。

如果声音连续而频谱卡住，优先检查这一层，不要直接归因于解码速度。

### 2.6 最后验证播放状态机

至少覆盖：

- 从其他格式切入新格式；
- 新格式之间连续切换；
- 播放开始后一两秒内 seek；
- 前、中、后多个位置 seek；
- 暂停、恢复、切歌和播放到结尾；
- 解码失败时是否只报告错误，还是错误地自动推进队列。

“自动跳歌”是上层失败恢复的表现，不代表根因一定在队列。必须同时检查 Extractor、decoder 错误和 seek 后送入的首包。

## 3. APE 案例：实际踩到的坑

### 3.1 APE 需要按自身容器规则解复用

APE 接入需要解析 Descriptor、Header、Seek Table、`blocksPerFrame`、最终帧采样数和帧对齐。早期 seek 不稳定说明不能按普通文件的字节比例估算位置，必须将目标时间映射到 APE 帧，再使用 seek table 定位。

最终把应用生成的前两个压缩 packet 与 FFmpeg 官方 demuxer 对比：

| packet | size | MD5 | 结论 |
|---|---:|---|---|
| 1 | 67780 bytes | `eec59e9ca8d154b69871e6ff6a3b081b` | 应用与 FFmpeg 一致 |
| 2 | 106856 bytes | `f0883d9776ef3d6514a6802fc39dfdab` | 应用与 FFmpeg 一致 |

这证明当时的压缩帧构造已经正确，后续开头异响不应继续修改 `ApeExtractor`。

### 3.2 大帧暴露了频谱队列的时间模型问题

测试文件为 44100 Hz、双声道，`blocksPerFrame=73728`，单个 APE 帧约 1.672 秒。普通格式通常以更小、更均匀的块输出，因此原有频谱队列的问题没有明显暴露。

APE 一次送入大量 PCM 后，频谱数据的到达速度与实际播放速度分离，造成频谱短暂停住或追赶。最终策略是：

- 队列容量按输入 burst 动态适配，并保持边界；
- 频谱消费时钟跟随实际播放状态；
- seek、切歌和 flush 时重置旁路时间线。

这属于通用音频链修正，并非 APE 特判；其他格式只是没有触发原有边界。

### 3.3 严格静音样本帮助排除错误层级

测试 APE 经标准 FFmpeg 解码后，`0–0.897574s` 是数字静音，但应用曾在 `0:00` 发出异常声音，随后短暂无声，约 `0:01` 后半才正常播放。

另制作了前约 0.9 秒严格静音、之后为正弦波的 ALAC 对照文件。ALAC 在相同应用链路中正常静音，因此排除了：

- 上一首歌曲残留；
- 通用 AudioTrack 启动瞬态；
- 共用 float DSP 输出链；
- 频谱分析器；
- 通用 FFmpeg Renderer 路径。

剩余范围被收敛到 APE 大帧触发的 native PCM 输出过程。

### 3.4 根因：JNI 输出缓冲区扩容后写指针丢失

该 APE 首帧解码为 float PCM 时需要：

```text
73728 帧 × 2 声道 × 4 bytes = 589824 bytes
```

而 FFmpeg JNI 初始输出缓冲区约为 131070 bytes，因此首帧必然扩容。扩容回调返回新缓冲区的基地址，已写数据虽然被保留，但 native 写指针没有恢复到已写数据末尾。后续子帧从缓冲区开头继续写，覆盖了前面的 PCM。

关键修复位于 `third_party/media3-ffmpeg-decoder/src/main/jni/ffmpeg_jni.cc`：

```cpp
outputBuffer += outSize;
```

也就是扩容后重新加上已写字节数。这个 bug 并非 APE 解码算法错误，而是 APE 的超大单帧稳定触发了通用 JNI 扩容路径。

修复后，设备端首帧 PCM SHA-256 与标准 FFmpeg 完全一致，前 100 ms 峰值为 0，开头异响消失。

## 4. 症状到排查层级的映射

| 症状 | 优先检查 | 不要立即假定 |
|---|---|---|
| 文件不入库 | 扩展名、扫描规则、MIME、元数据探测 | FFmpeg 不支持 |
| 点击后立即跳歌 | 支持路由、prepare 错误、首包、decoder 初始化 | 队列逻辑错误 |
| 一拖进度就跳歌 | seek table、目标帧、seek 后首包和时间戳 | AudioTrack 故障 |
| 声音正常但频谱卡顿 | PCM burst、队列容量、播放时钟、flush | 解码器算力不足 |
| 开头异响或错误静音 | 源 PCM 基准、decoder 输出、buffer position/扩容 | 上一首残留 |
| 只在某格式出现 | 该格式触发的帧大小、格式转换或边界路径 | 必然是该格式的 Extractor |
| packet 与标准工具一致但声音错误 | decoder、JNI、PCM 格式和下游处理 | 继续重写 packet |

## 5. 新格式验收清单

### 静态与单元级

- [ ] 扩展名、MIME、扫描和元数据字段一致。
- [ ] 正常、截断、非法及边界文件头有测试。
- [ ] 首帧、普通帧、最后一帧和对齐规则有测试。
- [ ] duration 和 seek 映射有测试。
- [ ] Renderer/decoder 支持策略有测试。
- [ ] 最大合理 PCM burst 有明确计算，并覆盖输出缓冲区扩容。
- [ ] 频谱/旁路队列容量有界，不随整首歌曲或曲库规模增长。

### 基准对比

- [ ] 前几个压缩 packet 的 offset、size、PTS、duration 和哈希与标准工具一致。
- [ ] 首个解码 buffer 的长度、静音位置、峰值和 PCM 哈希与标准工具一致。
- [ ] seek 后首包和对应 PCM 与目标时间一致。

### 实机

- [ ] 首播正常，无异常声音、长空白或错误跳歌。
- [ ] 连续切入、切出该格式至少五次。
- [ ] 开头、中间和结尾附近 seek 正常。
- [ ] 暂停/恢复、耳机或蓝牙路由变化后正常。
- [ ] 频谱与听感同步，无卡住、突跳或旧歌曲残留。
- [ ] 播放到结尾能够正常推进队列。
- [ ] 检查 decoder 错误、AudioTrack underrun 和非预期状态重建日志。

### 收尾

- [ ] 移除临时 PCM、buffer 和 packet 探针。
- [ ] 保留可重复执行的格式契约脚本或测试。
- [ ] clean build，确认最终 APK 使用的是新构建的 native `.so`。
- [ ] 明确记录“构建通过”和“实机验收通过”的不同证据。
- [ ] 若改动可能降低音质，实施或默认启用前先取得用户明确同意。

## 6. 排障原则

1. **先建立基准，再改代码。** 源文件的静音、帧大小和 packet 内容必须由标准工具确认。
2. **一次只证明一层。** Extractor packet 一致后，就把注意力移到 decoder；PCM 一致后，再检查 sink 和状态机。
3. **优先构造对照实验。** 相同 PCM 特征、不同容器的控制文件，比大量泛化日志更容易排除共享链路。
4. **格式独有不等于格式代码独有。** 新格式经常只是第一个触发通用缓冲区、时间模型或状态机边界的输入。
5. **大块输出是一级测试维度。** 除文件大小、采样率和位深外，还要测“单次 decoder 输出大小”。
6. **探针应只读、有界、可删除。** 不应为了观察问题而改变 buffer position、调度或音频内容。
7. **听感用于发现问题，数据用于确定根因。** 最终修复应能由 packet/PCM/状态证据解释，再由实机听感验收。
