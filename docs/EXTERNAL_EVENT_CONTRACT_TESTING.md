# 外部事件契约测试

> 目的：防止“内部状态机测试很完整，但生产环境根本没有交付测试所假设的输入”再次发生。

## 1. 这次播放计数为什么漏测

旧测试详细覆盖了播放统计状态机：回调顺序、重复回调、跨 batch 隔离、mediaId、位置回卷和连续 generation。问题在于这些测试直接向 `PlayerController` listener 注入了理想化的 Media3 回调，默认每次真实循环都会到达：

```text
真实播放循环
  → REPEAT transition
  → AUTO position discontinuity
  → Controller onEvents
  → 统计状态机
```

真实链路并不满足这个假设。Service 所持有的原始 Player 能看到每次循环，但 `MediaController` 会根据前后 `PlayerInfo` 的差异决定是否向 Controller 派发回调。连续单曲循环可能产生完全相同的 `duration → 0` 信息，后续回调因此被合并；通知歌词的 `replaceMediaItem` 又可能让元数据更新表现成带旧 reason 的 transition。

所以旧测试实际证明的是：

> 回调完整到达时，状态机可以正确识别。

它没有证明：

> 每次真实边界都能产生状态机依赖的回调。

这是一个**输入真实性缺口**，不是简单的分支覆盖率不足。

## 2. 可复用的失效模型

只要业务事实需要经过外部组件、跨进程/跨线程桥接或观察层转换，就可能出现同类问题：

```text
真实事实 F
  → 权威事件源 A
  → 框架/IPC/Flow/回调适配器 B
  → 业务输入 C
  → 状态机 D
  → 用户可见结果 R
```

单测直接构造 `C` 只能验证 `C → D → R`。如果生产缺陷发生在 `F → A → B → C`，增加再多状态机排列组合也无法发现。

常见转换风险包括：

- 去重、合并、采样、节流或只保留最新值；
- 相等性判断吞掉连续的相同事件；
- 缓存值、重放值或陈旧 reason 被当成新事实；
- 跨线程、跨进程或生命周期切换导致丢失、乱序或重复；
- 一个 API 表示“命令已发出”，却被当成“行为已发生”；
- mock 允许生产实现永远不会产生的回调组合；
- 第一次事件正常，连续同构事件才暴露合并问题。

## 3. 先确定事实所有权

为每项重要行为写清楚三个角色：

| 角色 | 问题 | 播放计数示例 |
|---|---|---|
| 权威事实源 | 谁最先知道事实确实发生？ | Service 原始 Player 的自动 discontinuity |
| 传输/观察层 | 谁只负责转发或展示状态？ | MediaSession / MediaController |
| 业务裁决层 | 谁把事实转为业务结果？ | `PlaybackStatisticsTracker` |

规则：

1. 不从观察层的派生状态反推权威事实，除非其 API 明确保证无损交付。
2. 命令、意图、状态快照和已发生事件必须使用不同术语。
3. 如果业务要求“每次都处理”，事件不能只依赖会合并相等值的状态通道。
4. 无法确认所有权时，先做最小契约探针，不先扩写状态机。

## 4. 新增或修改功能时的测试顺序

### 硬性开发规则：所有 Player 写操作都必须审计观察者副作用

任何会改变 Player、播放列表或 MediaItem 的操作，即使产品意图只是刷新元数据，也必须在实现和评审时审计它会向观察者暴露什么变化。

Player 写操作包括但不限于：

- `setMediaItem(s)`、`addMediaItem(s)`、`removeMediaItem(s)`、`moveMediaItem(s)`；
- `replaceMediaItem(s)`，包括封面、标题、歌词等仅元数据更新；
- `seekTo`、切换当前索引、上一首/下一首；
- `prepare`、`play`、`pause`、`stop`、`playWhenReady`；
- repeat、shuffle、播放速度、音高及其他播放参数修改。

每次写操作必须逐项审计：

1. 是否改变 timeline、当前 MediaItem、索引、位置、播放状态或 `isPlaying`；
2. 会产生哪些 transition、discontinuity、timeline、metadata、state 或 Session 回调；
3. 回调经过 MediaSession/MediaController 后是否会合并、重放、改写 reason 或延迟；
4. 哪些观察者会响应：播放统计、收听时长、最近播放、队列镜像、持久化恢复、通知歌词、当前曲 UI、进度和诊断；
5. 每个观察者副作用属于**必须发生、允许发生、禁止发生**中的哪一类；
6. 是否存在“写入触发观察者，观察者又写回 Player”的反馈环。

最低测试要求：

- 为必须发生的副作用写至少一个正例；
- 为禁止发生的副作用写至少一个负例；
- 元数据写操作必须证明不会冒充播放边界、用户动作或新播放会话；
- 队列/索引写操作必须检查当前曲、进度、统计和持久化是否被意外重置；
- 如果结论依赖 Media3 实际派发哪些回调，必须补真实组件契约测试，不能只用手工 listener callback。

审计结果应记录在变更对应的测试名称、测试矩阵或设计文档中。仅凭“这个写操作看起来不会影响统计/UI”不能视为完成审计。

### 4.1 写出生产链路

在测试前列出实际路径，不只列被测类：

```text
触发动作
→ 最底层可观察事实
→ 框架或系统边界
→ App 适配器
→ 领域状态机
→ 持久化/UI/输出
```

每个箭头都要回答：是否可能丢失、合并、重放、乱序、延迟或改写字段？

### 4.2 分层验证

至少考虑以下四层；不要求所有改动都建真机测试，但必须明确哪些层没有验证。

1. **纯逻辑测试**：验证状态机在可信领域事实下的规则、边界和负例。
2. **适配器/接线测试**：验证框架对象如何转换成领域事实，尤其是字段、reason、ID 和生命周期。
3. **真实组件契约测试**：使用真实框架组件验证事件是否真的产生和传递，例如真实 MediaSession、Room、ContentResolver 或解码器。
4. **设备/系统验收**：验证依赖 OEM、硬件、系统服务、进程生命周期或真实文件提供者的部分。

高层测试不能代替低层规则测试；低层组合穷举也不能代替真实组件契约。

### 4.3 同时记录上下游

契约测试不要只断言最终结果。至少记录：

- 权威源实际发生次数；
- 观察层实际交付次数；
- 业务层接受/拒绝次数及原因；
- 最终副作用次数。

推荐断言形态：

```text
权威事实 = 3
传输事件 = 3
业务会话 = 3
持久化写入 = 3
```

如果某层允许合并，应明确断言合并规则，而不是默认一一对应。

### 4.4 必测连续同构事件

单次成功不足以证明事件通道可靠。重要事件至少测试：

- 连续三次完全相同的事件；
- 事件之间插入无关状态/元数据更新；
- 暂停、恢复、重连或生命周期重建后继续发生；
- 相邻事件字段只改变一个值；
- 命令重复、回调重复和回调缺失；
- 正例前后各放一个容易混淆的负例。

“连续三次”不是固定产品规则，而是发现 equality suppression、只保留最新值和 generation 泄漏的低成本探针。

## 5. Mock 使用约束

Mock 适合验证本模块如何响应输入，不适合证明外部系统会产生该输入。

使用 mock 回调前必须回答：

1. 这个回调序列是否在真实组件上观察过，或由官方契约保证？
2. mock 是否绕过了生产中的相等性判断、序列化、线程调度或生命周期？
3. 测试是否手动调用了生产环境不会连续调用的方法？
4. 如果外部层少发一次、重复一次或改变顺序，当前测试能否发现？

出现以下情况时，必须补真实组件契约测试或明确记录验证缺口：

- 业务正确性依赖回调次数；
- 依赖 reason、旧值/新值、索引或时间戳组合；
- 框架内部存在 diff、distinct、debounce、缓存或批处理；
- 涉及 Binder、Service、通知、MediaSession、ContentProvider、SAF、蓝牙或硬件；
- bug 只在第二次及以后出现；
- mock 测试全绿但用户仍能稳定复现。

## 6. 跨模块风险清单

以后检查下列领域时，优先寻找“权威源与观察层是否混淆”：

- **播放与音频**：命令派发不等于开始出声；Controller 状态不一定等于原始 Player/AudioTrack 事实。
- **通知与系统媒体控制**：元数据刷新、Controller 重连和系统重放不能冒充新的用户动作。
- **Room / Flow / Compose state**：状态流可能合并相等值；一次状态变化不等于每个中间事件都被观察。
- **扫描与 SAF**：扫描请求成功不等于文件可读、权限持久化或 provider 已完成写入。
- **蓝牙、音频焦点和 noisy 事件**：模拟 callback 不能证明 OEM 实际派发顺序。
- **队列与持久化恢复**：保存命令、落盘完成、Service 恢复和 UI 镜像是四个不同事实。
- **动画与布局**：目标 state 正确不等于真实帧序列无跳变；静态截图无法证明时序。
- **解析与解码**：解析出的 metadata 不等于真实解码路径使用了该格式或参数。

## 7. Bug 修复评审清单

修复涉及外部事件时，评审至少逐项确认：

- [ ] 用一句话定义要统计/触发的真实事实，而不是某个 callback 名称。
- [ ] 指定事实的权威来源。
- [ ] 所有 Player 写操作已列出观察者，并将副作用标为必须、允许或禁止。
- [ ] 元数据、队列和播放参数写入均检查了 timeline/transition/discontinuity/state 回调。
- [ ] 画出从权威源到最终副作用的完整生产路径。
- [ ] 标出所有可能合并、缓存、重放、延迟和跨生命周期的边界。
- [ ] 纯状态机正例与负例均覆盖。
- [ ] 适配器字段映射和无关事件覆盖。
- [ ] 至少一个测试使用真实外部组件，不手工伪造关键回调。
- [ ] 连续三个同构事件覆盖。
- [ ] 同时断言权威事件数和最终副作用数。
- [ ] 明确列出仍未覆盖的 OEM、硬件、进程或时序条件。
- [ ] 诊断日志能区分“事实没发生、事件没传到、状态机拒绝、写入失败”。

## 8. 本次播放计数的落地结论

自动下一首和单曲循环现在由 Service 原始 Player 确认真实边界，通过 MediaSession custom command 传递领域事件；MediaController 的 AUTO/REPEAT 回调只用于状态同步，不能自行创建自动播放会话。

对应测试同时观察原始 Player 回卷和最终播放 session，并覆盖连续三轮循环、通知歌词元数据替换、自然下一首、显式重播、暂停恢复、手动 seek 和 Controller 接入。

这套实现解决的是当前播放统计问题；它不能证明所有 OEM、进程死亡和后台生命周期都已覆盖。未覆盖部分仍应在发布前设备矩阵中明确验收。
